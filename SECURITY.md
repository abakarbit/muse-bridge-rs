# Security Policy

## Reporting a vulnerability

Please report vulnerabilities privately via GitHub's
[private vulnerability reporting](https://github.com/abakarbit/muse-bridge-rs/security/advisories/new)
("Security → Report a vulnerability") instead of opening a public issue.
You can expect an acknowledgement within a few days. There is no bug bounty;
this is a personal open-source project.

## Security model

- **Keys**: bearer keys are generated by `keygen`, shown once, and stored
  only as SHA-256 hashes with a `user` or `worker` role. Roles are enforced
  per endpoint — a user key cannot claim jobs, a worker key cannot submit
  chat requests. Rotate by `keygen` + `keydel`; revocation is immediate.
- **Blast radius**: a leaked *worker* key lets an attacker submit fake
  answers; a leaked *user* key lets an attacker enqueue jobs (bounded by
  `BRIDGE_MAX_PENDING` backpressure). Neither leaks stored data — the bridge
  keeps no answer history beyond job TTLs.
- **Transport**: the default bind is loopback (plus a detected private
  overlay/Tailscale address). Enable `BRIDGE_TLS_CERT`/`BRIDGE_TLS_KEY`
  before exposing the bridge anywhere else, and firewall it regardless.
- **Operational hygiene**: keep key files, the SQLite database, and gateway
  configs at mode `600`, outside the repository. The worker wrapper
  (`scripts/worker_poll.py`) exists so an automated agent can poll and
  answer without ever reading the raw worker key — prefer that pattern
  over handing credentials to an LLM-driven process.
- **Gateway surface**: if you pair this bridge with a chat gateway such as
  PicoClaw, restrict channels to your own chat ID(s) and keep the gateway's
  tool/exec surface disabled or hardened — a chat message must never become
  a shell command on the agent host. The reference config in `examples/`
  ships with all gateway tools disabled.

## Supported versions

Only the latest release on `main` is supported.
